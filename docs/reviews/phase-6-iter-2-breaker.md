# Phase 6, iteration 2 — break
Summary: 0 blockers, 2 high, 3 medium, 3 low. Tests added: backend/tests/adversarial/test_phase6_iter2_break.py (4 tests, all fail now).

Lens: two users at once, refresh mid-flow, slow network, API down. Tried against the live link (modest: 15 concurrent demo journeys, about 140 requests) and against a local `python -m app --site --no-reload`, using `AI_MODE=live` with an invalid key and with `ANTHROPIC_BASE_URL` pointed at a local server that hangs for 30 s (`AI_TIMEOUT_SECONDS=4`).

## Findings

### [high] One visitor's quote reading freezes the whole site while the AI service is slow
Expected: a slow Claude API slows only the visitor whose document is being read. Other visitors, including anyone running the demo journey, carry on.
Actual: `POST /money/read` (backend/app/api/money.py, `read_documents`) is an `async def` route that calls the blocking `read_quote` (the Anthropic SDK call) directly on the event loop. While it waits, nothing else on the server is answered. The constitution check already moves its reader to a worker thread (`run_in_threadpool`, with a comment saying why). The quote reader does not. In the worst case each document waits up to `AI_TIMEOUT_SECONDS` × 3 tries (`max_retries=2`), which is about 3 minutes at the default 60 s, and one request can carry 11 documents (10 files plus pasted text). That would freeze the whole site for over half an hour.
Reproduce: locally, `ANTHROPIC_BASE_URL=http://127.0.0.1:8799` (a server that hangs), `AI_MODE=live`, `AI_TIMEOUT_SECONDS=4`. POST /api/money/read with `text=Quote from Pizza Place: 20 pizzas at $15 each, total $300`, and 1 s later GET /api/health. The health check took 12.8 s. The read returned 200 after 13.8 s with a clear "could not read" problem, which is correct on its own. Test: `test_reading_a_quote_while_the_ai_service_is_slow_does_not_stall_other_visitors` (another request waits 1.5 s behind a 1.5 s stand-in reader).

### [high] Money check and event packet keep showing the old result after the inputs change (edit after checking)
Expected: after any input changes, the screen does not show a verdict, total or deadline worked out from the old inputs. Either clear the result or mark it "out of date, check again". The year plan already does this: it recomputes on every change.
Actual (from the code, frontend/src/pages/MoneyCheck.tsx): only line edits (`setLine`) and loading the demo clear `report`. Changing the event fields (expected attendance, ticketed, open to all, venue, date), "USG money already received this year", "Events USG already funded this semester", the ticked attachments or the fund leaves the old report on screen. Its verdict, "Food per person" figure, "USG total this year" figure and "draft allowed" stay unchanged.
Concrete case, checked against the API: Culture Night, 150 people, food $5,250 ($35.00 per person), not ticketed. The check returns `office_decides` with the draft allowed and no red. With expected attendance at 100, the same budget is `red` (`usg-food-cap`, $52.50 per person). On the page, changing 150 to 100 after checking keeps showing $35.00 per person with no red item.
EventPacket.tsx has the same flaw: editing the date, venue or attributes after "Build the packet" does not clear `packet`. The dated timeline for the old date stays under a form showing the new date, and the packet heading shows only the event name, not the date.
Mitigation that holds: `/money/draft` and `/usg/send` recheck on the server, so no draft or sent application is made from the stale result. The display is still wrong for the inputs shown (lens items 1 and 2). This is frontend code, so I added no backend test. Reproduce in a browser: Money check → Load the demo club's culture night budget → change catering to $35 per person, ticketed No, delete the DJ line → Check the budget → change Expected attendance to 100. The report still says food is $35.00 per person and offers the draft.

### [medium] A second approval replaces the denial reason the club already reads
Expected: once a reason is approved and visible to the club, it cannot be silently replaced. Phase 5 iteration 3 blocked a new draft for exactly this reason (409).
Actual: `denial-approve` (backend/app/api/usg.py) does not check `denial_status == "approved"`. A second reviewer with the page still open, or a double submit after a slow response, overwrites `denial_approved_text` and `denial_approved_by`, and the club's status page changes. A related race the spec does not cover: reviewer A drafts with reason X, reviewer B drafts with reason Y (this overwrites `denial_rule_ids`), then A approves A's text about X. The club reads a text about X while the record says Y, because the approval does not name which draft or rule ids it approves.
Reproduce: test `test_a_second_approval_cannot_replace_the_reason_the_club_already_reads` (the second approve returns 200 and the club then reads "Denied: DJ fees are not fundable.").

### [medium] Several instances starting together on a fresh database fail to create the tables
Expected: start-up is safe when more than one process starts at once. `.replit` deploys with `deploymentTarget = "autoscale"`, start.sh runs `seed_demo.py` (which runs `init_db`), and the site's lifespan runs `init_db` again. The lifespan already tolerates the same race for rule versions (`IntegrityError` caught), but not for `create_all`.
Actual: concurrent `Base.metadata.create_all` on a fresh database fails with `OperationalError: table clubs already exists`. 4 concurrent `scripts/seed_demo.py` runs on a fresh SQLite file: 3 failed with a traceback (start.sh only warns). In the site's lifespan the same exception stops that instance from starting. This only affects a fresh or reset database, such as a new Postgres database or a SQLite fallback after a redeploy.
Reproduce: test `test_tables_are_created_safely_when_several_processes_start_at_once` (6 engines on one fresh file, released together; it fails every time).

### [medium] The demo's gap email is replayed only from one exact path; a deep link to /money/gap gets the plain fallback
Expected (README step 5, PLAN Phase 6 "recorded AI responses available as a fallback"): the demo's outreach email shows its recorded paragraph whichever way the visitor reaches the funding gap page.
Actual: the recording key covers the event name. Only `event_name = "Culture night"` (set when the page is opened from the year plan's "Close the gap") replays. Opening /money/gap directly (fresh tab, shared link, bookmark) and pressing "Fill in the demo club's example" sends an empty event name. In live mode with the API down or slow this gives "Greenlight could not draft the paragraph just now; it wrote a plain one." The fallback is clear and honest, but it reads "Dear The manager, Golden Lantern Kitchen, We are planning our event, …". The same happens with any other event name, for example "Culture Night" typed with a capital N.
Reproduce: AI_MODE=live, invalid key. POST /api/gap/email with the GapHelper DEMO_EMAIL fields and `event_name` "" or "Spring banquet": the notes show the fallback. With "Culture night": no note, so the recording was replayed.

### [low] A missing /assets/ file returns the page (200, text/html) instead of 404
Expected: a request for a missing script or style file returns a 404.
Actual: `SinglePageApp` serves index.html for every missing path, including `/assets/index-<old hash>.js`. After a redeploy, a tab that kept the old index.html (or a cached copy) asks for the old bundle, gets HTML, and the browser refuses it as a module script: a blank page with no message. `/favicon.ico`, `/.env` and `/.git/config` also return the page with 200. No file leaks, but the status is misleading.
Reproduce: `curl -i https://greenlight--manasman1.replit.app/assets/nope.js` returns 200 text/html. Test: `test_a_missing_script_file_is_a_404_not_the_page`.

### [low] API documentation is public on the live site (question)
`create_site` turns off docs for the outer app (`docs_url=None, openapi_url=None`), which suggests the intent to hide them. The mounted API still serves `/api/docs` and `/api/openapi.json` (live: 200), listing the reviewer routes and their header. Nothing secret is exposed, and every reviewer route needs the passcode. The spec is silent; the team should decide whether to keep it.

### [low] AI-unavailable answers use status 422, and the frontend's fetch has no timeout
`POST /events/parse` and `/money/fund` answer 422 ("could not read … just now") when the AI service is down. 422 means the request was invalid; 503 would tell a client to retry. The message itself is clear. Separately, `getJson`/`postJson` in frontend/src/api/client.ts set no timeout. With a slow network the button stays on "Checking…" until the browser gives up, with no message. Spec silent; listed for the team.

## What I tried that held up
- Live link, 5 parallel demo journeys × 3 rounds (sample constitution check, year plan, culture-night packet, red then clean money check, application draft, gap email, accuracy): every request returned 200. Every run found the planted contradiction (clause-ii-a-1) and the missing clause (clause-iii-g-1). The budget went red and then "office decides" with the draft allowed, never green. The gap email replayed with no fallback note. Each journey took 4.8 to 7.3 s of server time.
- AI service down (`AI_MODE=live`, invalid key or hanging endpoint), demo inputs: constitution, gap email and application draft are all replayed from recordings, with no network call.
- AI service down, other inputs: constitution check is `overall: red` with GPA and membership clauses `needs_look`, `reader.used: false` and a plain message. It is never green. read-events returns a per-line error and `facts: null`. events/parse and money/fund return a clear "fill in the form / choose the fund yourself". money/read reports the document as not read.
- Path tricks: `/..%2f..%2fbackend%2f.env`, `/%2e%2e/%2e%2e/README.md`, `/assets/..%2f..%2f..%2fREADME.md`, `/api/../README.md` (with `--path-as-is`): none served a file outside frontend/dist. Unknown `/api/...` routes give a JSON 404, not the page. `/api/health/` redirects to `https://<host>/api/health` behind the proxy (proxy headers honoured).
- Deep links: `/money/gap`, `/usg`, `/money/check`, `/events/packet` all load the page locally and on the live link. The year plan saves to localStorage and recomputes on every change (stale results are discarded via a request counter). Router state survives a refresh.
- Site with no built frontend: a clear `RuntimeError` naming `npm run build`. No DATABASE_URL: start.sh warns, and SQLite is anchored to backend/. `postgres://` and `postgresql://` are rewritten to `postgresql+psycopg://`.
- Seeding run twice in a row: one copy of the demo club. The seeded database rows are not read by any API route (the demo plan comes from data/demo/club.json), so a seed failure cannot break the journey.
- Two clubs sending to the USG screen at once: references and tokens are random, and each club reads only its own application with its token.
