## Findings

### [medium] Ports set only in `.env` move the frontend proxy but not the backend
Expected: `CLAUDE.md` ("Ports and addresses") says two copies can run "by setting these, in the shell or in `.env`". Setting `BACKEND_PORT` in `.env` should therefore move both the backend and the proxy target.
Actual: Vite reads `../.env` (`loadEnv(mode, "..", "")`), so the proxy follows `.env`. The documented backend command `uvicorn … --port ${BACKEND_PORT:-8000}` is expanded by the shell, which never reads `.env`, so the backend stays on 8000. The proxy then forwards to a port where nothing listens, or worse, to another copy's backend on 8000.
Reproduce (in a clone):
```
sed -i '' 's/^BACKEND_PORT=8000/BACKEND_PORT=8011/; s/^FRONTEND_PORT=5173/FRONTEND_PORT=5186/' .env
env -u BACKEND_PORT -u FRONTEND_PORT zsh -c 'cd backend; echo "--port ${BACKEND_PORT:-8000}"'   # prints: --port 8000
cd frontend && env -u BACKEND_PORT -u FRONTEND_PORT npm run dev                                   # Local: http://localhost:5186/, proxies /api to 8011
```
Either make the backend start command read `.env` (for example a small `python -m app` entry point that reads `BACKEND_PORT` through settings), or change `CLAUDE.md` to say ports must be set in the shell. `.env.example` also implies `.env` works ("Change these to run two copies side by side").

### [medium] `seed_demo.py` seeds a database the running backend never reads
Expected: `python scripts/seed_demo.py` ("load the demo club", run from the repo root as `CLAUDE.md` says) loads data the app then shows.
Actual: `DATABASE_URL=sqlite:///./greenlight.db` depends on the working directory. The seed script runs from the repo root and writes `$CLONE/greenlight.db`. The backend runs from `backend/` and reads `$CLONE/backend/greenlight.db`.
Reproduce:
```
cd $CLONE && source backend/.venv/bin/activate && python scripts/seed_demo.py
# Seeded demo data: 1 clubs, 2 users, 1 year_plans, 5 events
python -c "import sqlite3; [print(p, sqlite3.connect(p).execute('select count(*) from clubs').fetchone()) for p in ('greenlight.db','backend/greenlight.db')]"
# greenlight.db (1,)
# backend/greenlight.db (0,)
```
Resolve a relative SQLite path against a fixed directory (for example `REPO_ROOT` or `BACKEND_DIR`), or put an absolute default in `.env.example`. Not visible yet because no Phase 0 route reads clubs, but the Phase 6 demo depends on it.

### [medium] `usg-approved-vendor` shows red, certain, although the vendor list it relies on is unverified
Expected: PROJECT_CONTEXT section 8 lists "the approved vendor list (USG) and approved caterer list" under "Confirm first". `CLAUDE.md`: "Do not encode anything PROJECT_CONTEXT marks unverified as if it were certain." A vendor-not-on-list result built on this rule will be shown as a certain red. That contradicts `usg-vendor-list`'s own message. This is not a wrong green, but it is an unverified input shown as certain. The rule sentence "We will not accept a vendor not on the list" is verified, and section 7 asks for red, so exit criterion 4 still passes literally. Reproduce: `curl -s http://127.0.0.1:<BACKEND_PORT>/rules/usg-approved-vendor | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['display_severity'], d['depends_on'], d['params'])"` prints `red [] {'vendor_list_rules': ['usg-vendor-list']}`.
